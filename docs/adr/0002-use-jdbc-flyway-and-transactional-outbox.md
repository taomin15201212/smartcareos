# Use JDBC, Flyway, and a transactional outbox for alarms

## 来源事实

《招聘信息汇总.md》明确提及 MySQL、消息队列、MQTT 设备事件与报警业务。这些信息支持关系型持久化和异步消息集成方向，但没有规定数据访问框架、事件表结构或投递实现。

## 架构推演

告警模块使用 Spring JDBC 明确表达聚合读写和乐观锁；Flyway 管理可审计的数据库迁移；告警主表、状态轨迹和 Outbox 事件在同一个本地事务中提交。本地默认运行配置使用 MySQL 兼容模式的 H2 文件数据库；本机 MySQL `smartcareos` 数据库保留为显式 `mysql` profile。

Outbox 只保存跨上下文所需的标识、状态、严重度、版本、动作和操作者，不复制老人健康详情。事件发布器后续独立实现，并以 `published_at` 驱动至少一次投递。

## 决策理由

- 避免“数据库已提交但消息未发送”或相反的双写不一致。
- 数据库唯一键保证来源事件幂等，版本条件更新防止并发覆盖。
- 显式 SQL 便于核查告警这一高风险流程的持久化语义。
- H2 默认配置保留轻量离线运行能力；MySQL profile 用于方言、并发、索引和生产方向验证。

## 后果

- 当前 Outbox 仅保证事务写入，不代表消息已发布。
- 发布器和消费者必须支持重试、重复投递与消费幂等。
- H2 只用于开发和自动化测试；上线前必须在真实 MySQL 上完成迁移、并发、索引和恢复验证。
